2. Core Updates Requested by Haroon
2.1 Raise a Case — Cross-Team Collaboration
Current Concept
The Raise a Case module was demonstrated based on the ZD manual.
Required Updates
ZD should support cases/tasks being raised to another department or team, not only within the requestor's own department.
The workflow should support:
Request Raised → Assigned Team → Acknowledgement → Investigation / Response → Back-and-Forth Communication → Resolution
Required functionality
Requestor can raise a case to another team.
Case should land with the relevant team.
Case may also be routed to the relevant Line Manager where required.
Receiving team must acknowledge the request.
Initial acknowledgement should be tracked against a 24-hour expectation.
Requestor and receiving team should have a proper back-and-forth communication mechanism.
The receiving team should be able to provide updates without closing the case.
If the receiving team does not respond within the required period, the system should allow escalation.
Escalation should be visible and traceable.
Communication history should form part of the case timeline.
Objective
Increase internal communication and collaboration between departments, rather than forcing communication to happen outside ZD.
3. Priority, TAT and SLA
Haroon specifically highlighted that Priority needs to be separated from TAT/SLA.
Required Updates
The system should support:
Priority assignment.
Priority levels.
TAT tracking.
SLA tracking.
Priority changes during the lifecycle.
Visibility of how priority changes affect the case/task.
Escalation based on missed response/TAT requirements.
Important distinction
TAT/SLA = time-based performance measurement
Priority = business importance/urgency
Priority should therefore not simply replace SLA/TAT.
The system should allow the priority of an item to change during its lifecycle while maintaining the historical record.

5. Visit Findings → RFI / Relevant Team
Haroon highlighted that individual findings should be assignable to the relevant PM/team.
Therefore:
Visit → Finding → Relevant Team → RFI / Action
should be supported within ZD.
A visit should not become one large unstructured record.
Instead, individual findings should be capable of becoming actionable items.

For a project/site, the system should allow users to see:
Previous visits
Previous findings
Previous issues
Previous actions
Previous evidence

Recurring problems
Historical status
This should allow the user to understand whether an issue is:
New / Recurring / Previously Resolved / Still Outstanding

Drive
Excel sheets
should be retained as backup/reference sources where required.
The implementation should therefore avoid immediately eliminating historical records stored in existing sources without an appropriate migration/backup strategy.

"Open a Project"
The terminology should be consistent across the system.

The Decisions Waiting on You section requires stronger action-oriented visibility.
Required Updates

What should I do today?

10. Lessons Learned
Lessons Learned was identified as an important module/functionality.
This should not be treated as a simple decision or case.
Core Principle
A Lesson Learned represents:
"What happened, why did it happen, and how can we improve in the future?"
It is therefore a future improvement mechanism, not a decision.
11. Lesson Learned — Escalation & Visibility
Haroon requested that Lessons Learned should have visibility at senior-management and audit levels.
When a Lesson Learned is raised:
Lesson Learned → Department Head Visibility → Audit Visibility → Learning Repository
The relevant Heads should be able to see the lessons generated from their departments.
Audit should also have visibility where appropriate.
12. Lesson Learned — Root Cause / Performance Analysis
Lessons Learned should be capable of capturing issues such as:
SLA/TAT took too long
Why did it take too long?
Where was the delay?
Which team/process caused the delay?
Was the delay internal or external?
Was there a dependency?
What should change?
What preventive action should be taken?
This creates a connection between operational performance and organisational learning.
13. Learning Summary Page
A dedicated Learning Summary page should be introduced.
The page should consolidate lessons learned and allow management to understand:
Number of lessons learned
Major recurring issues
Root causes
Departments involved
Process weaknesses
TAT/SLA-related problems
Recommended improvements
Open improvement actions
Closed improvements
Recurring lessons
The objective is to turn lessons learned into institutional knowledge and process improvement.
14. Lesson Learned — Department Coverage
The discipline/department classification needs to be expanded.
It should not be limited to the currently available departments.
Additional departments such as Legal should be supported.
The department structure should therefore be aligned with the broader organisational hierarchy.
15. Cross-System Collaboration
Haroon highlighted that ZD should not operate in isolation.
Where a lesson, case, task or finding requires collaboration with another system/module, users should be able to:
Link the item
Refer it to another module/system
Maintain the relationship
Track the originating item
Maintain visibility of the resulting action
The goal is to ensure that collaboration does not require users to manually recreate the same information in multiple places.
16. Senior Management Collaboration
A key organisational requirement was identified:
Collaboration should not be limited to junior employees across departments.
Sometimes departments need to coordinate at a senior-management level.
ZD should therefore support collaboration/escalation involving:
Department Heads
Senior Managers
Relevant Line Managers
Cross-functional leadership
The system should make it possible to involve the appropriate senior person when normal team-level collaboration is insufficient.

27. Time Definitions — Wait / Hold / In Progress
A key point requiring clarification was identified.
The system needs clear definitions for:
Wait
Time during which an item is waiting for another person/team/action.
Hold / Blocking Time
Time during which progress is intentionally or externally blocked.
In Progress
Time during which the responsible team is actively working on the item.
Important discussion point
It was suggested that Wait may also need to be counted as part of In Progress for certain reporting purposes.
This needs to be formally defined before implementation of the final performance calculations.
28. Own Time / Hold Time
The concept of Own Time was discussed.
This should be reviewed against the concept of:
Hold Time / Blocking Time
The final data model should establish exactly what each metric means and avoid overlapping calculations.
29. Delivery Cycle
The Delivery Cycle requires careful treatment because delays and approvals can affect the reported performance of senior managers.
Important consideration
When a Director signs off, the timing of that approval can currently reflect negatively on the senior manager/director in the delivery-cycle metrics.
The calculation therefore needs to distinguish between:
Team execution time
Waiting for approval
Director approval time
External dependency
PM activity
Actual delivery time
30. MD Approval
It was specifically discussed that:
MD Approval time should be removed from Delivery Time.
This should be reflected in the calculation logic once the final metric definitions are confirmed.
31. PM / Asana Context in Delivery
The current operational delivery process is heavily supported by:
Asana
PM processes
The ZD Delivery Cycle should therefore account for the actual operating model rather than assuming all delivery activity occurs directly inside ZD.
Integration/linkage with PM activity should be considered where necessary.

37. Target Operating Model Emerging from the Meeting
The overall direction from the review is that ZD should evolve from being primarily a request/task tracking system into a connected operational coordination and accountability platform.
The intended model is:
Request / Issue / Visit / Project Activity
↓
Structured Workflow
↓
Responsible Team
↓
TAT + Priority + SLA
↓
Communication / Collaboration
↓
Escalation where required
↓
Resolution / Approval
↓
Historical Record
↓
Performance Measurement
↓
Lesson Learned
↓
Management Insight / Process Improvement
This should be the guiding architecture for the next design and development iteration.
